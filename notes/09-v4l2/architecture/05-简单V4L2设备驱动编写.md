# 简单 V4L2 虚拟设备驱动编写

初学 V4L2 驱动，一下涌入很多概念、术语，设备模型，关键结构体等，看了好几天视频和资料后，有点小心得，就是脑子里没有一张清楚的图：APP 在干什么，V4L2 Core 在干什么，vb2 在干什么，真正的驱动又在干什么。

## 1. 先记住老师的三层模型

理解 V4L2 驱动，先按三层看，这个也是课程的介绍流程。

```text
┌──────────────────────────────────────────────┐
│ 第一层：APP                                   │
│ open / ioctl / mmap / poll / read             │
│ QUERYCAP / S_FMT / REQBUFS / QBUF / DQBUF     │
└───────────────────────┬──────────────────────┘
                        │ 标准 V4L2 ABI
                        v
┌──────────────────────────────────────────────┐
│ 第二层：V4L2 Core + videobuf2                 │
│ video_ioctl2 分发 ioctl                       │
│ vb2 管理 buffer：分配、映射、排队、等待、出队 │
└───────────────────────┬──────────────────────┘
                        │ 回调驱动提供的 ops
                        v
┌──────────────────────────────────────────────┐
│ 第三层：具体驱动/硬件                          │
│ 回答支持什么格式                              │
│ 接收 APP 交来的空 buffer                      │
│ 启动/停止硬件                                 │
│ 一帧完成时填 buffer 并调用 vb2_buffer_done()  │
└──────────────────────────────────────────────┘
```

这三层各自的职责很固定：

```text
APP 层：
  不关心硬件怎么采集，只按 V4L2 标准调用 ioctl。

V4L2 Core/vb2 层：
  不知道你的硬件寄存器，但知道 V4L2 ioctl 该怎么分发，
  也知道 buffer 从 APP 到驱动、再从驱动回 APP 的通用状态机。

驱动层：
  真正知道硬件，知道支持什么格式，知道怎么启动采集，
  知道一帧什么时候完成。
```

所以写驱动时，不是在从零实现一个字符设备；你是在填 V4L2 Core 和 vb2 留的几个“空”。

## 2. 再建立 buffer 的“空桶/满桶”模型

视频采集不是一次性读一个数据，而是一帧一帧连续流动。为了不断流，APP 和驱动之间要循环使用多个 buffer。

可以把 buffer 想成桶：

```text
空桶：APP 已经准备好，里面还没有新图像。
满桶：驱动已经填入一帧图像，APP 可以取走处理。
```

整个 streaming 流程就是：

```text
1. APP 申请一批桶
   VIDIOC_REQBUFS

2. APP 把桶映射到用户空间
   VIDIOC_QUERYBUF + mmap

3. APP 把空桶交给驱动
   VIDIOC_QBUF

4. APP 启动采集
   VIDIOC_STREAMON

5. 驱动/硬件产生一帧
   取一个空桶，填入图像数据

6. 驱动告诉 vb2：这个桶满了
   vb2_buffer_done(..., VB2_BUF_STATE_DONE)

7. APP 取回满桶
   VIDIOC_DQBUF

8. APP 用完后再把它作为空桶交回去
   再次 VIDIOC_QBUF
```

重点不是背 ioctl 名字，而是知道 buffer 状态怎么走：

```text
APP 空闲 buffer
  --QBUF-->
驱动持有的空 buffer
  --硬件填充一帧-->
驱动通知完成
  --vb2_buffer_done-->
vb2 完成队列
  --DQBUF-->
APP 得到满 buffer
  --处理完再 QBUF-->
循环
```

只要这条线清楚，V4L2 驱动就不再是一堆散乱函数。

## 3. 写一个简单 V4L2 驱动

根据老师的思路来看，驱动编写本质上就是填空题：

```text
1. 注册入口
   让系统出现 /dev/videoX。

2. ioctl 回答
   告诉 APP：我是什么设备、支持什么格式、什么分辨率。

3. vb2 队列
   告诉 vb2：buffer 怎么分配、每个 buffer 多大、支持 mmap/read/userptr 哪些方式。

4. 硬件回调
   APP 把 buffer 交给驱动时怎么办；
   APP 启动采集时怎么办；
   一帧完成时怎么通知；
   停止采集时怎么清理。
```

对应到代码，就是这些对象：

```c
static struct video_device g_vdev;
static struct v4l2_device g_v4l2_dev;
static struct vb2_queue g_vb_queue;

static struct list_head g_queued_bufs;
static struct timer_list g_virtual_timer;
static struct mutex g_vb_queue_lock;
static struct mutex g_v4l2_lock;
```

这里可以这样理解：

```text
video_device
  代表 /dev/videoX。APP 能打开这个节点，是它注册出来的。

v4l2_device
  V4L2 设备实例的容器。简单驱动里存在感不强，复杂设备里更重要。

vb2_queue
  buffer 队列总管。REQBUFS/QBUF/DQBUF/STREAMON/STREAMOFF 都围着它转。

g_queued_bufs
  驱动自己维护的“空桶队列”。APP QBUF 后，buffer 就被放到这里。

g_virtual_timer
  虚拟硬件。真实硬件是一帧中断/DMA完成/USB完成；这里用 timer 模拟。
```

## 4. 第一步：注册 `/dev/videoX`

APP 必须先能打开一个设备节点：

```c
ret = video_register_device(&g_vdev, VFL_TYPE_GRABBER, -1);
```

这个调用成功后，系统里就会出现一个 `/dev/videoX`。

`g_vdev` 里最关键的是两个指针：

```c
static struct video_device g_vdev = {
    .name      = "100ask_virtual_video",
    .release   = video_device_release_empty,
    .fops      = &virtual_fops,
    .ioctl_ops = &virtual_ioctl_ops,
};
```

```text
fops
  文件操作入口。open、mmap、poll、ioctl 从这里进来。

ioctl_ops
  V4L2 标准 ioctl 对应的驱动回调。
```

注册前还要把 `video_device` 和 `v4l2_device` 关联起来：

```c
g_v4l2_dev.release = virtual_video_release;
strcpy(g_v4l2_dev.name, "virtual_v4l2");
ret = v4l2_device_register(NULL, &g_v4l2_dev);

g_vdev.v4l2_dev = &g_v4l2_dev;
g_vdev.lock = &g_v4l2_lock;
```

这里的目的就是：让 V4L2 Core 知道“这个 video_device 属于哪个 V4L2 设备实例”。

## 5. 第二步：把文件操作交给 V4L2/vb2 通用函数

文件操作不用自己来实现，直接用 `v4l2_file_operations`现有的:

> 这里开始还再想，为什么这里不是每个驱动自己实现？
>
> 其实这里道理很简单，这部分就是V4L2 Core 存在的意义，
>
> 应为这些行为都是标准化的， V4L2 直接维护一套标准的就可以了

```c
static const struct v4l2_file_operations virtual_fops = {
    .owner          = THIS_MODULE,
    .open           = v4l2_fh_open,
    .release        = vb2_fop_release,
    .read           = vb2_fop_read,
    .poll           = vb2_fop_poll,
    .mmap           = vb2_fop_mmap,
    .unlocked_ioctl = video_ioctl2,
};
```

这几个函数的意义：

```text
v4l2_fh_open
  建立 V4L2 file handle。

vb2_fop_release
  关闭文件时释放/停止 vb2 队列相关资源。

vb2_fop_read
  支持 read() 方式取帧。

vb2_fop_poll
  支持 poll/select 等待帧完成。

vb2_fop_mmap
  支持 APP mmap buffer。

video_ioctl2
  V4L2 ioctl 总入口。它会根据 ioctl 命令号，调用 video_device->ioctl_ops。
```

所以 APP 调一个 ioctl 时，路径是：

```text
APP ioctl(fd, VIDIOC_QUERYCAP, &cap)
  -> virtual_fops.unlocked_ioctl
  -> video_ioctl2
  -> V4L2 Core 根据命令号分发
  -> virtual_ioctl_ops.vidioc_querycap
  -> virtual_querycap()
```

`video_ioctl2` 是 V4L2 Core 给驱动的 ioctl 分发器。驱动不需要自己写一个大 `switch(cmd)`。

## 6. 第三步：实现能力和  ioctl

APP 一上来通常会问：你是什么设备？支持什么格式？当前格式是什么？能不能设置成某个格式？

这部分由驱动自己回答，因为只有驱动知道硬件能力。

### 6.1 `VIDIOC_QUERYCAP`：说明自己是什么设备

```c
static int virtual_querycap(struct file *file, void *fh,
                            struct v4l2_capability *cap)
{
    strlcpy(cap->driver, "100ask_virtual_video", sizeof(cap->driver));
    strlcpy(cap->card, "no-card", sizeof(cap->card));
    cap->device_caps = V4L2_CAP_VIDEO_CAPTURE |
                       V4L2_CAP_STREAMING |
                       V4L2_CAP_READWRITE;
    cap->capabilities = cap->device_caps | V4L2_CAP_DEVICE_CAPS;

    return 0;
}
```

三个能力要理解：

```text
V4L2_CAP_VIDEO_CAPTURE
  我是视频采集设备。

V4L2_CAP_STREAMING
  我支持 REQBUFS/QBUF/DQBUF/STREAMON/STREAMOFF 这种 streaming 方式。

V4L2_CAP_READWRITE
  我也支持 read() 方式。
```

### 6.2 `ENUM_FMT / S_FMT / G_FMT`：说明图像格式

这个虚拟驱动只支持 MJPEG、800x600。

枚举格式：

```c
static int virtual_enum_fmt_cap(struct file *file, void *priv,
                                struct v4l2_fmtdesc *f)
{
    if (f->index > 0)
        return -EINVAL;

    strlcpy(f->description, "100ask motion jpeg", sizeof(f->description));
    f->pixelformat = V4L2_PIX_FMT_MJPEG;
    return 0;
}
```

设置格式：

```c
static int virtual_s_fmt_cap(struct file *file, void *priv,
                             struct v4l2_format *f)
{
    if (f->type != V4L2_BUF_TYPE_VIDEO_CAPTURE)
        return -EINVAL;

    if (f->fmt.pix.pixelformat != V4L2_PIX_FMT_MJPEG)
        return -EINVAL;

    f->fmt.pix.width = 800;
    f->fmt.pix.height = 600;
    return 0;
}
```

获取当前格式：

```c
static int virtual_g_fmt(struct file *file, void *priv,
                         struct v4l2_format *f)
{
    struct v4l2_pix_format *pix = &f->fmt.pix;

    pix->width = 800;
    pix->height = 600;
    pix->field = V4L2_FIELD_NONE;
    pix->pixelformat = V4L2_PIX_FMT_MJPEG;
    pix->bytesperline = 0;
    return 0;
}
```

分辨率枚举：

```c
static int virtual_enum_framesizes(struct file *file, void *fh,
                                   struct v4l2_frmsizeenum *fsize)
{
    if (fsize->index > 0)
        return -EINVAL;

    fsize->type = V4L2_FRMSIZE_TYPE_DISCRETE;
    fsize->discrete.width = 800;
    fsize->discrete.height = 600;
    return 0;
}
```

这些函数要挂到 `v4l2_ioctl_ops`：

```c
static const struct v4l2_ioctl_ops virtual_ioctl_ops = {
    .vidioc_querycap          = virtual_querycap,
    .vidioc_enum_fmt_vid_cap  = virtual_enum_fmt_cap,
    .vidioc_s_fmt_vid_cap     = virtual_s_fmt_cap,
    .vidioc_g_fmt_vid_cap     = virtual_g_fmt,
    .vidioc_enum_framesizes   = virtual_enum_framesizes,

    .vidioc_reqbufs           = vb2_ioctl_reqbufs,
    .vidioc_create_bufs       = vb2_ioctl_create_bufs,
    .vidioc_prepare_buf       = vb2_ioctl_prepare_buf,
    .vidioc_querybuf          = vb2_ioctl_querybuf,
    .vidioc_qbuf              = vb2_ioctl_qbuf,
    .vidioc_dqbuf             = vb2_ioctl_dqbuf,
    .vidioc_streamon          = vb2_ioctl_streamon,
    .vidioc_streamoff         = vb2_ioctl_streamoff,
};
```

这里有一个非常重要的分界：

```text
能力/格式类 ioctl：驱动自己实现。
REQBUFS/QBUF/DQBUF/STREAMON/STREAMOFF：交给 vb2 通用函数。
```

为什么后者能交给 vb2？因为 buffer 生命周期大部分是通用逻辑，vb2 只在关键时刻回调驱动。

## 7. 第四步：理解 vb2 内部的“三组 ops”

老师讲的三层模型里，还有一个很关键的局部模型：`vb2_queue` 里面有三组 ops。

> 这个 3个很关键！就是不同层的结构要怎么转换，这个好像跟IIO 还是什么有点像，不太理解为什么不同层要用不同的结构体表示

```text
vb2_queue
  ├── vb2_buf_ops：APP 的 v4l2_buffer 和内核 vb2_buffer 怎么互相转换
  ├── vb2_mem_ops：buffer 内存怎么分配、映射、取虚拟地址/DMA 地址
  └── vb2_ops：和具体硬件相关的动作，驱动主要实现这一组
```

简单总结如下：

```text
buf_ops 管“信息怎么抄”
  APP 传进来的是 struct v4l2_buffer；
  内核里面管理的是 struct vb2_buffer；
  两者之间 index、plane、timestamp、bytesused 等信息怎么转换，靠 buf_ops。

mem_ops 管“内存从哪来”
  是 vmalloc？连续 DMA 内存？userptr？dmabuf？
  mmap 怎么做？内核虚拟地址怎么取？这些靠 mem_ops。

vb2_ops 管“硬件要什么”
  需要几个 buffer？每个 buffer 多大？
  APP QBUF 后怎么交给硬件？
  STREAMON 怎么启动硬件？
  STREAMOFF 怎么停止硬件？这些靠驱动实现。
```

这就是为什么初始化 `vb2_queue` 时要写：

```c
g_vb_queue.ops = &virtul_vb2_ops;
g_vb_queue.mem_ops = &vb2_vmalloc_memops;
```

`buf_ops` 没看到显式设置，是因为 `vb2_queue_init()` 里会给 V4L2 场景设置通用的 `v4l2_buf_ops`，这个视频里面有讲；

写简单驱动时，主要关注两组：

```text
mem_ops
  选哪种内存管理方式。
  虚拟摄像头用 vb2_vmalloc_memops。
  真实 DMA 采集常见会用 vb2_dma_contig_memops 等。

vb2_ops
 要实现的硬件相关回调。
```

## 8. 第五步：初始化 vb2_queue

`vb2_queue` 是 buffer 队列的总管。初始化它，就是告诉 vb2：这个设备的 buffer 是什么类型、支持什么 IO 方式、内存怎么来、硬件回调在哪里。

```c
g_vb_queue.type = V4L2_BUF_TYPE_VIDEO_CAPTURE;
g_vb_queue.io_modes = VB2_MMAP | VB2_USERPTR | VB2_READ;
g_vb_queue.drv_priv = NULL;
g_vb_queue.buf_struct_size = sizeof(struct virtual_frame_buf);
g_vb_queue.ops = &virtul_vb2_ops;
g_vb_queue.mem_ops = &vb2_vmalloc_memops;
g_vb_queue.timestamp_flags = V4L2_BUF_FLAG_TIMESTAMP_MONOTONIC;

ret = vb2_queue_init(&g_vb_queue);
```

逐项翻译理解防止忘记：

```text
type
  这个队列是哪类 buffer。普通摄像头采集是 V4L2_BUF_TYPE_VIDEO_CAPTURE。
  它必须和 APP 传入的 type、S_FMT/G_FMT 里的 type 保持一致。

io_modes
  APP 可以用哪些方式拿 buffer。
  这里支持 MMAP、USERPTR、READ。

buf_struct_size
  vb2 分配 buffer 对象时，额外分配多大的驱动私有 buffer 结构。
  这里是 struct virtual_frame_buf。

ops
  硬件相关回调。REQBUFS/QBUF/STREAMON/STREAMOFF 过程中会调用它。

mem_ops
  内存管理方法。这里用 vmalloc，所以后面可以用 vb2_plane_vaddr() 取虚拟地址。

timestamp_flags
  时间戳类型。
```

然后把队列关联到到 `video_device` 设备上：

```c
mutex_init(&g_vb_queue_lock);

g_vdev.queue = &g_vb_queue;
g_vdev.queue->lock = &g_vb_queue_lock;
```

从这一步开始，`vb2_ioctl_reqbufs/qbuf/dqbuf` 才知道该操作哪个队列。

## 9. 第六步：定义驱动自己的 buffer

vb2 有自己的通用 buffer，驱动通常还要在外面包一层，放自己需要的信息。

```c
struct virtual_frame_buf {
    struct vb2_v4l2_buffer vb;
    struct list_head list;
};
```

这里的 `list` 是驱动自己用来排队的。APP QBUF 之后，buffer 会进入驱动的 `g_queued_bufs` 链表：

```text
g_queued_bufs = 驱动当前持有的空 buffer 队列
```

从 `struct vb2_buffer` 找回驱动自己的 buffer：

```c
struct vb2_v4l2_buffer *vbuf = to_vb2_v4l2_buffer(vb);
struct virtual_frame_buf *buf =
        container_of(vbuf, struct virtual_frame_buf, vb);
```

这句代码背后的意思是：vb2 只认识通用 buffer，但驱动要找到自己包在外面的结构体，才能把它挂到自己的链表里。

## 10. 第七步：实现 vb2_ops

这是驱动和 vb2 配合最关键的一组函数：

```c
static const struct vb2_ops virtul_vb2_ops = {
    .queue_setup     = virtual_queue_setup,
    .buf_queue       = virtual_buf_queue,
    .start_streaming = virtual_start_streaming,
    .stop_streaming  = virtual_stop_streaming,
    .wait_prepare    = vb2_ops_wait_prepare,
    .wait_finish     = vb2_ops_wait_finish,
};
```

把它们放进 APP 流程里看，就很清楚。

### 10.1 `queue_setup`：APP 申请 buffer 前，vb2 问驱动“你要什么样的桶？”

APP：

```c
ioctl(fd, VIDIOC_REQBUFS, &req);
```

内核：

```text
VIDIOC_REQBUFS
  -> vb2_ioctl_reqbufs
  -> vb2_core_reqbufs
  -> virtual_queue_setup()
```

驱动回答：

```c
static int virtual_queue_setup(struct vb2_queue *vq,
        unsigned int *nbuffers,
        unsigned int *nplanes,
        unsigned int sizes[],
        struct device *alloc_devs[])
{
    if (vq->num_buffers + *nbuffers < 8)
        *nbuffers = 8 - vq->num_buffers;

    *nplanes = 1;
    sizes[0] = PAGE_ALIGN(800 * 600 * 2);

    return 0;
}
```

它只回答三件事：

```text
要几个 buffer？
  至少 8 个。

每个 buffer 几个 plane？
  1 个。

每个 plane 多大？
  PAGE_ALIGN(800 * 600 * 2)。
```

注意：`queue_setup` 不填数据，也不启动硬件。它只是告诉 vb2 怎么分配 buffer。

### 10.2 `buf_queue`：APP 交出一个空 buffer，vb2 把它转交给驱动

APP：

```c
ioctl(fd, VIDIOC_QBUF, &buf);
```

内核：

```text
VIDIOC_QBUF
  -> vb2_ioctl_qbuf
  -> vb2_core_qbuf
  -> virtual_buf_queue()
```

驱动：

```c
static void virtual_buf_queue(struct vb2_buffer *vb)
{
    struct vb2_v4l2_buffer *vbuf = to_vb2_v4l2_buffer(vb);
    struct virtual_frame_buf *buf =
            container_of(vbuf, struct virtual_frame_buf, vb);

    list_add_tail(&buf->list, &g_queued_bufs);
}
```

这一步的本质：

```text
APP 给了一个空桶。
vb2 检查并记录状态。
驱动把这个空桶放进自己的待填充队列。
```

真实硬件里，这一步常常会把 buffer 的 DMA 地址交给硬件；虚拟驱动没有硬件，所以只是挂链表。

### 10.3 `start_streaming`：APP 说“开始采集”，驱动启动硬件

APP：

```c
ioctl(fd, VIDIOC_STREAMON, &type);
```

内核：

```text
VIDIOC_STREAMON
  -> vb2_ioctl_streamon
  -> vb2_core_streamon
  -> virtual_start_streaming()
```

虚拟驱动用 timer 模拟硬件：

```c
static int virtual_start_streaming(struct vb2_queue *vq,
                                   unsigned int count)
{
#if LINUX_VERSION_CODE < KERNEL_VERSION(4, 15, 0)
    setup_timer(&g_virtual_timer, virtual_timer_expire, 0);
#else
    timer_setup(&g_virtual_timer, virtual_timer_expire, 0);
#endif

    g_virtual_timer.expires = jiffies + HZ / 30;
    add_timer(&g_virtual_timer);

    return 0;
}
```

真实驱动可能会做：

```text
开时钟
配置寄存器
配置 DMA
打开中断
启动 sensor/CSI/USB 传输
```

虚拟驱动只做一件事：让 timer 1/30 秒触发一次，用它假装“硬件来了一帧”。

### 10.4 一帧完成：驱动填 buffer，然后 `vb2_buffer_done()`

这一步是 V4L2 驱动最核心的动作。

虚拟驱动的 timer 到期函数可以这样理解：

```text
timer 到期，等价于“硬件产生一帧”
  -> 从 g_queued_bufs 取一个空 buffer
  -> 得到这个 buffer 的内核虚拟地址
  -> 拷贝一张 JPEG 数据进去
  -> 设置本帧有效字节数
  -> 调用 vb2_buffer_done(DONE)
  -> 重新启动 timer，准备下一帧
```

取一个空 buffer：

```c
static struct virtual_frame_buf *virtual_get_next_buf(void)
{
    struct virtual_frame_buf *buf = NULL;

    if (list_empty(&g_queued_bufs))
        goto leave;

    buf = list_entry(g_queued_bufs.next,
                     struct virtual_frame_buf, list);
    list_del(&buf->list);

leave:
    return buf;
}
```

填数据并通知完成：

```c
ptr = vb2_plane_vaddr(&buf->vb.vb2_buf, 0);

if (g_copy_cnt <= 60) {
    memcpy(ptr, red, sizeof(red));
    vb2_set_plane_payload(&buf->vb.vb2_buf, 0, sizeof(red));
} else if (g_copy_cnt <= 120) {
    memcpy(ptr, green, sizeof(green));
    vb2_set_plane_payload(&buf->vb.vb2_buf, 0, sizeof(green));
} else {
    memcpy(ptr, blue, sizeof(blue));
    vb2_set_plane_payload(&buf->vb.vb2_buf, 0, sizeof(blue));
}

vb2_buffer_done(&buf->vb.vb2_buf, VB2_BUF_STATE_DONE);
```

这里有三个关键点：

```text
vb2_plane_vaddr()
  因为使用 vb2_vmalloc_memops，所以可以取内核虚拟地址，然后 memcpy。

vb2_set_plane_payload()
  设置这一帧真正有效的数据大小，也就是 APP 看到的 bytesused。
  MJPEG 是压缩格式，每帧大小按实际 JPEG 数据大小来。

vb2_buffer_done()
  驱动告诉 vb2：这个 buffer 已经填好了，可以让 APP DQBUF 取走。
```

有点需要注意： `vb2_buffer_done()`。它是“驱动完成一帧”和“APP 能取到一帧”之间关键消息。

### 10.5 `DQBUF`：APP 取满 buffer，主要由 vb2 完成

APP：

```c
ioctl(fd, VIDIOC_DQBUF, &buf);
```

驱动没有自己实现 `dqbuf`，因为 ioctl 关联的是：

```c
.vidioc_dqbuf = vb2_ioctl_dqbuf,
```

vb2 能不能让 `DQBUF` 返回，取决于之前有没有 buffer 被驱动标记为完成，也就是 buffer_done：

```c
vb2_buffer_done(&buf->vb.vb2_buf, VB2_BUF_STATE_DONE);
```

关键流程如下：

```text
QBUF 让驱动得到空 buffer。
vb2_buffer_done 让 vb2 得到完成 buffer。
DQBUF 让 APP 得到完成 buffer。
这里一开始也容易觉得太绕了；
```

### 10.6 `stop_streaming`：停止采集时归还所有驱动持有的 buffer

APP：

```c
ioctl(fd, VIDIOC_STREAMOFF, &type);
```

驱动：

```c
static void virtual_stop_streaming(struct vb2_queue *vq)
{
    del_timer(&g_virtual_timer);

    while (!list_empty(&g_queued_bufs)) {
        struct virtual_frame_buf *buf;

        buf = list_entry(g_queued_bufs.next,
                         struct virtual_frame_buf, list);
        list_del(&buf->list);
        vb2_buffer_done(&buf->vb.vb2_buf, VB2_BUF_STATE_ERROR);
    }
}
```

这里容易忽略：停止时，驱动手里可能还有 APP 交来的空 buffer，但还没来得及填。必须把它们还给 vb2。

为什么用 `VB2_BUF_STATE_ERROR`？

```text
参考资料
因为这些 buffer 没有有效图像数据，不能标记为 DONE；
但它们也不能继续留在驱动手里，所以用 ERROR 状态归还。
```

## 11. 把完整流程串起来

现在把所有东西放回三层模型：

```text
APP open("/dev/videoX")
  -> V4L2 Core / v4l2_fh_open

APP VIDIOC_QUERYCAP
  -> video_ioctl2
  -> 驱动 virtual_querycap

APP VIDIOC_ENUM_FMT / G_FMT / S_FMT
  -> video_ioctl2
  -> 驱动回答格式能力

APP VIDIOC_REQBUFS
  -> vb2_ioctl_reqbufs
  -> vb2_ops.queue_setup
  -> mem_ops 分配 buffer 内存

APP VIDIOC_QUERYBUF + mmap
  -> vb2_ioctl_querybuf / vb2_fop_mmap
  -> APP 得到可访问的 buffer

APP VIDIOC_QBUF
  -> vb2_ioctl_qbuf
  -> buf_ops 把 v4l2_buffer 信息转成 vb2_buffer 信息
  -> vb2_ops.buf_queue
  -> 驱动把空 buffer 放入 g_queued_bufs

APP VIDIOC_STREAMON
  -> vb2_ioctl_streamon
  -> vb2_ops.start_streaming
  -> 驱动启动 timer/真实硬件

硬件完成一帧
  -> 驱动取一个空 buffer
  -> 填入图像数据
  -> 设置 payload
  -> vb2_buffer_done(DONE)

APP VIDIOC_DQBUF
  -> vb2_ioctl_dqbuf
  -> APP 取回完成 buffer

APP 再次 VIDIOC_QBUF
  -> buffer 循环使用

APP VIDIOC_STREAMOFF
  -> vb2_ioctl_streamoff
  -> vb2_ops.stop_streaming
  -> 驱动停止硬件并归还未完成 buffer
```

这就是简单 V4L2 capture 驱动的完整骨架。

## 12. 从虚拟驱动迁移到真实硬件驱动时可能的变化点

下面部分也是结合业务代码参考，不一定完全准：

```text
start_streaming
  虚拟驱动：启动 timer。
  真实驱动：启动 sensor、CSI、DMA、USB URB、中断等。

buf_queue
  虚拟驱动：把 buffer 挂到 g_queued_bufs。
  真实驱动：通常要把 buffer 的 DMA 地址交给硬件，或者放入硬件待处理队列。

一帧完成的位置
  虚拟驱动：timer 回调。
  真实驱动：中断、DMA done、USB complete、CSI frame done。

填数据方式
  虚拟驱动：CPU memcpy 到 vmalloc buffer。
  真实驱动：多数情况是硬件 DMA 直接写 buffer。

mem_ops
  虚拟驱动：vb2_vmalloc_memops。
  真实 DMA 驱动：可能使用 vb2_dma_contig_memops 或其他 allocator。
```

但是有一件事不变：

```text
一帧完成后，驱动最终都要调用 vb2_buffer_done()。
```



## 13. 最容易混的点

记录下学习过程中一些容易混淆的点；

### 13.1 `QBUF` 不是取数据，是交空 buffer

`QBUF` 的方向是：

```text
APP -> 驱动
```

APP 把一个空 buffer 交给驱动。驱动还没填数据。

### 13.2 `DQBUF` 才是取完成帧

`DQBUF` 的方向是：

```text
驱动/vb2 -> APP
```

APP 能取到的前提是驱动已经 `vb2_buffer_done()`。

### 13.3 `queue_setup` 不启动硬件

`queue_setup` 只回答 buffer 分配要求：几个 buffer、几个 plane、每个 plane 多大。

### 13.4 `start_streaming` 不一定马上有数据

`STREAMON` 只是启动采集。真正有数据，要等硬件完成一帧，然后驱动调用 `vb2_buffer_done()`。

### 13.5 `STREAMOFF` 必须归还 buffer

停止采集时，驱动手里的 buffer 必须全部归还给 vb2。完成的用 `DONE`，没完成的用 `ERROR`。

### 13.6 `V4L2_BUF_TYPE_VIDEO_CAPTURE` 要一致

普通摄像头采集要用：

```c
V4L2_BUF_TYPE_VIDEO_CAPTURE
```

它应该在这些地方一致：

```text
querycap 能力
S_FMT/G_FMT type
vb2_queue.type
APP reqbuf/qbuf/dqbuf/streamon 的 type
```

只要类型不一致，APP 和驱动就可能对不上。

## 14. 模块职责

参考课程资料总结 ：

| 模块 | 作用 | 典型函数/结构 |
| --- | --- | --- |
| APP | 使用者，按标准 ioctl 交空 buffer、取满 buffer | `VIDIOC_REQBUFS`、`VIDIOC_QBUF`、`VIDIOC_DQBUF` |
| V4L2 Core | ioctl 分发器，把标准命令转到驱动回调 | `video_ioctl2`、`v4l2_ioctl_ops` |
| vb2 | buffer 管家，负责分配、映射、排队、等待、出队 | `vb2_queue`、`vb2_ioctl_qbuf`、`vb2_ioctl_dqbuf` |
| vb2_buf_ops | APP buffer 信息和内核 buffer 信息互转 | `fill_vb2_buffer`、`fill_user_buffer` |
| vb2_mem_ops | buffer 内存怎么来、怎么 mmap、怎么取地址 | `vb2_vmalloc_memops`、`vb2_plane_vaddr` |
| vb2_ops | 驱动回答硬件相关问题 | `queue_setup`、`buf_queue`、`start_streaming`、`stop_streaming` |
| 具体驱动 | 知道硬件，负责启动采集和完成帧 | `vb2_buffer_done`、中断/DMA/timer 回调 |

## 15. 一句话总结

写 V4L2 capture 驱动时，脑子里不要先背结构体，一定要先明白这条流水线：

```text
APP 申请 buffer
  -> vb2 分配/管理 buffer
  -> APP QBUF 交空 buffer
  -> 驱动 buf_queue 收下空 buffer
  -> APP STREAMON 启动采集
  -> 硬件完成一帧
  -> 驱动填好 buffer 并 vb2_buffer_done
  -> APP DQBUF 取满 buffer
  -> APP 再 QBUF 循环使用
```

`video_device` 解决“APP 怎么找到我”，`video_ioctl2` 解决“ioctl 怎么分发”，`vb2_queue` 解决“buffer 怎么管理”，`vb2_ops` 解决“驱动和硬件怎么接上”，`vb2_buffer_done()` 解决“驱动怎么把完成帧还给 APP”。

这几个点连起来，简单 V4L2 驱动就通了。要完全熟悉还是的要项目经验才行，目前也只能大概看着文档知道怎么回事，按照参考流程来一步一步的查找；
