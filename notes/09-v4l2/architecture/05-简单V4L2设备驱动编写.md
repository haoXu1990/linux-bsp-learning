# 简单 V4L2 设备驱动编写：按老师虚拟摄像头代码理解

这一篇只讲老师 `06_virtual_driver` 这组代码里的主线：怎样从 0 搭一个能被 APP 打开、查询格式、申请 buffer、启动采集、取到一帧数据的 V4L2 虚拟摄像头驱动。

这里不重点讨论参考对象叫什么。参考对象只是代码来源；我们真正要抓的是流程、步骤、关键点：V4L2 Core 怎么调用驱动，vb2 怎么管理 buffer，驱动什么时候拿到空 buffer，什么时候把完成帧还给 APP。

老师这个虚拟驱动不是一个真实摄像头，也不是完整 USB/MIPI 摄像头驱动。它用 `vb2_vmalloc_memops` 分配内存，用 timer 模拟硬件中断，用 `red/green/blue` 三组 MJPEG 图片数组模拟“硬件采集到的一帧数据”。这样可以先把寄存器、DMA、中断、sensor 配置这些干扰拿掉，只看 V4L2 capture 驱动的骨架。

## 1. 四份代码分别在补什么

```text
01_virtual_driver_framework
  先搭 V4L2/vb2 框架：file_operations、ioctl_ops、video_device、
  v4l2_device、vb2_queue。

02_virtual_driver_hardware
  补“硬件能力”：支持什么格式、什么分辨率、buffer 怎么排队、
  STREAMON/STREAMOFF 时驱动该做什么。

03_virtual_driver_hardware_datatransfer
  补“数据传输”：APP QBUF 后，buffer 进入驱动队列；
  timer 模拟硬件每 1/30 秒产生一帧；
  驱动填充 buffer 并调用 vb2_buffer_done()。

04_virtual_driver_ok
  修成最终可用版：补 G_FMT、修正 queue type、初始化锁、
  注册 video_device、STREAMOFF 时归还未完成 buffer。
```

所以这节课的主线可以压缩成一句话：

```text
注册 /dev/videoX
  -> 回答 APP 的能力/格式查询
  -> 用 vb2 管理 APP 申请的 buffer
  -> APP QBUF 后驱动拿到空 buffer
  -> STREAMON 后模拟硬件开始产帧
  -> 一帧完成时填 buffer 并 vb2_buffer_done()
  -> APP DQBUF 取走完成帧
  -> STREAMOFF 停止并归还剩余 buffer
```

## 2. 一个最小 V4L2 capture 驱动要回答的问题

老师的虚拟摄像头驱动，核心就是回答 6 个问题。

```text
1. /dev/videoX 从哪里来？
   video_device + video_register_device()

2. APP open/read/mmap/poll/ioctl 进来后谁处理？
   v4l2_file_operations + video_ioctl2 + v4l2_ioctl_ops

3. APP 查询能力时，驱动说自己是什么设备？
   vidioc_querycap

4. APP 查询/设置格式时，驱动说自己支持什么图像格式？
   enum_fmt / g_fmt / s_fmt / enum_framesizes

5. APP 申请、映射、入队、出队 buffer 时谁管理？
   vb2_queue + vb2_ioctl_reqbufs/qbuf/dqbuf/streamon/streamoff

6. 一帧数据什么时候完成？
   驱动拿到可用 buffer，填数据，然后调用 vb2_buffer_done()
```

老师代码里使用的主要全局对象是：

```c
static struct video_device g_vdev;
static struct v4l2_device g_v4l2_dev;
static struct vb2_queue g_vb_queue;

static struct list_head g_queued_bufs;
static struct timer_list g_virtual_timer;
static struct mutex g_vb_queue_lock;
static struct mutex g_v4l2_lock;
```

学习这份代码时，先不要急着抽象成复杂私有结构体。老师用全局变量是为了让流程直观：哪个对象属于 V4L2，哪个对象属于 vb2，哪个队列属于驱动自己。

## 3. 第一步：注册 video_device，生成 `/dev/videoX`

APP 打开摄像头时打开的是 `/dev/videoX`。这个节点来自：

```c
ret = video_register_device(&g_vdev, VFL_TYPE_GRABBER, -1);
```

关键对象是 `struct video_device`：

```c
static struct video_device g_vdev = {
    .name      = "100ask_virtual_video",
    .release   = video_device_release_empty,
    .fops      = &virtual_fops,
    .ioctl_ops = &virtual_ioctl_ops,
};
```

字段含义：

```text
name
  设备名字，调试和查询时能看到。

release
  video_device 释放函数。老师这里是静态全局对象，所以用
  video_device_release_empty。

fops
  文件操作。APP 的 open/read/poll/mmap/ioctl 入口在这里。

ioctl_ops
  V4L2 ioctl 操作表。APP 调 VIDIOC_QUERYCAP、VIDIOC_S_FMT、
  VIDIOC_QBUF 等命令时，最后会分发到这里。
```

注册前还要注册并关联 `v4l2_device`：

```c
g_v4l2_dev.release = virtual_video_release;
strcpy(g_v4l2_dev.name, "virtual_v4l2");
ret = v4l2_device_register(NULL, &g_v4l2_dev);

g_vdev.v4l2_dev = &g_v4l2_dev;
g_vdev.lock = &g_v4l2_lock;
```

`v4l2_device` 可以先理解为这个 V4L2 设备实例的“总容器”。简单虚拟驱动里它看起来存在感不强；到了 MIPI/Media Controller 场景，它会和 subdev、media graph 关系更密切。

最终初始化顺序大概是：

```text
设置并初始化 vb2_queue
初始化 g_vb_queue_lock / g_v4l2_lock
设置 g_vdev.queue / g_vdev.lock
注册 v4l2_device
设置 g_vdev.v4l2_dev
注册 video_device，生成 /dev/videoX
初始化 g_queued_bufs
```

## 4. 第二步：准备 file_operations

老师代码里的 `virtual_fops` 是 APP 进入驱动的第一层入口：

```c
static const struct v4l2_file_operations virtual_fops = {
    .owner          = THIS_MODULE,
    .open           = v4l2_fh_open,
    .release        = vb2_fop_release,
    .read           = vb2_fop_read,
    .poll           = vb2_fop_poll,
    .mmap           = vb2_fop_mmap,
    .unlocked_ioctl = video_ioctl2,
};
```

关键点是：简单驱动不需要自己从头实现所有字符设备操作，V4L2 Core 和 vb2 已经提供了通用处理。

```text
open
  用 v4l2_fh_open 建立 V4L2 file handle。

release
  用 vb2_fop_release 关闭文件并处理 vb2 队列释放。

read
  用 vb2_fop_read 支持 read() 方式取帧。

poll
  用 vb2_fop_poll 支持 select/poll 等待帧完成。

mmap
  用 vb2_fop_mmap 支持 mmap buffer。

unlocked_ioctl
  用 video_ioctl2。它是 V4L2 ioctl 分发入口，会根据命令号调用
  virtual_ioctl_ops 里的具体回调。
```

例如 APP 调：

```c
ioctl(fd, VIDIOC_QUERYCAP, &cap);
```

内核路线是：

```text
APP ioctl
  -> virtual_fops.unlocked_ioctl
  -> video_ioctl2
  -> V4L2 Core 检查和分发
  -> virtual_ioctl_ops.vidioc_querycap
  -> virtual_querycap()
```

## 5. 第三步：声明设备能力

驱动首先要告诉 APP：“我是一个视频采集设备，支持 streaming，也支持 read/write 风格访问。”

```c
static int virtual_querycap(struct file *file, void *fh,
                            struct v4l2_capability *cap)
{
    strlcpy(cap->driver, "100ask_virtual_video", sizeof(cap->driver));
    strlcpy(cap->card, "no-card", sizeof(cap->card));
    cap->device_caps = V4L2_CAP_VIDEO_CAPTURE |
                       V4L2_CAP_STREAMING |
                       V4L2_CAP_READWRITE;
    cap->capabilities = cap->device_caps | V4L2_CAP_DEVICE_CAPS;

    return 0;
}
```

关键点：

```text
V4L2_CAP_VIDEO_CAPTURE
  说明这是普通视频采集设备，对应 V4L2_BUF_TYPE_VIDEO_CAPTURE。

V4L2_CAP_STREAMING
  说明支持 REQBUFS / QBUF / DQBUF / STREAMON / STREAMOFF。

V4L2_CAP_READWRITE
  说明支持 read() 方式。老师的 fops 里也挂了 vb2_fop_read。
```

## 6. 第四步：声明格式和分辨率

老师这个虚拟摄像头只支持一种格式：MJPEG。

```c
static int virtual_enum_fmt_cap(struct file *file, void *priv,
                                struct v4l2_fmtdesc *f)
{
    if (f->index > 0)
        return -EINVAL;

    strlcpy(f->description, "100ask motion jpeg", sizeof(f->description));
    f->pixelformat = V4L2_PIX_FMT_MJPEG;

    return 0;
}
```

`index > 0` 返回 `-EINVAL`，表示只有第 0 种格式。

设置格式时，驱动只接受普通视频采集类型和 MJPEG：

```c
static int virtual_s_fmt_cap(struct file *file, void *priv,
                             struct v4l2_format *f)
{
    if (f->type != V4L2_BUF_TYPE_VIDEO_CAPTURE)
        return -EINVAL;

    if (f->fmt.pix.pixelformat != V4L2_PIX_FMT_MJPEG)
        return -EINVAL;

    f->fmt.pix.width = 800;
    f->fmt.pix.height = 600;

    return 0;
}
```

最终版还补了 `G_FMT`：

```c
static int virtual_g_fmt(struct file *file, void *priv,
                         struct v4l2_format *f)
{
    struct v4l2_pix_format *pix = &f->fmt.pix;

    pix->width = 800;
    pix->height = 600;
    pix->field = V4L2_FIELD_NONE;
    pix->pixelformat = V4L2_PIX_FMT_MJPEG;
    pix->bytesperline = 0;

    return 0;
}
```

为什么要补 `G_FMT`？因为很多 APP 会先 `G_FMT` 看当前格式，再决定是否 `S_FMT`。如果驱动缺这个接口，有些测试程序或播放器会失败。

分辨率枚举：

```c
static int virtual_enum_framesizes(struct file *file, void *fh,
                                   struct v4l2_frmsizeenum *fsize)
{
    if (fsize->index > 0)
        return -EINVAL;

    fsize->type = V4L2_FRMSIZE_TYPE_DISCRETE;
    fsize->discrete.width = 800;
    fsize->discrete.height = 600;
    return 0;
}
```

这表示驱动只支持一个离散分辨率：`800x600`。

这些 ioctl 最后挂入：

```c
static const struct v4l2_ioctl_ops virtual_ioctl_ops = {
    .vidioc_querycap         = virtual_querycap,
    .vidioc_enum_fmt_vid_cap = virtual_enum_fmt_cap,
    .vidioc_s_fmt_vid_cap    = virtual_s_fmt_cap,
    .vidioc_enum_framesizes  = virtual_enum_framesizes,
    .vidioc_g_fmt_vid_cap    = virtual_g_fmt,

    .vidioc_reqbufs          = vb2_ioctl_reqbufs,
    .vidioc_create_bufs      = vb2_ioctl_create_bufs,
    .vidioc_prepare_buf      = vb2_ioctl_prepare_buf,
    .vidioc_querybuf         = vb2_ioctl_querybuf,
    .vidioc_qbuf             = vb2_ioctl_qbuf,
    .vidioc_dqbuf            = vb2_ioctl_dqbuf,
    .vidioc_streamon         = vb2_ioctl_streamon,
    .vidioc_streamoff        = vb2_ioctl_streamoff,
};
```

上半部分是驱动自己回答“能力和格式”；下半部分交给 vb2 处理 buffer 生命周期。

## 7. 第五步：定义驱动自己的 buffer

V4L2 streaming 的本质是：APP 和驱动共享一批 buffer。APP 把空 buffer 交给驱动，驱动填满后还给 APP。

老师定义了自己的 buffer：

```c
struct virtual_frame_buf {
    struct vb2_v4l2_buffer vb;
    struct list_head list;
};
```

关键点：

```text
struct vb2_v4l2_buffer vb
  必须有。它是 vb2/V4L2 认识的 buffer 对象。

struct list_head list
  驱动自己用。APP QBUF 后，驱动把这个 buffer 挂到
  g_queued_bufs 链表，表示“这个空 buffer 可以给硬件填数据”。
```

从 vb2 给你的 `struct vb2_buffer` 找回驱动自己的 buffer：

```c
struct vb2_v4l2_buffer *vbuf = to_vb2_v4l2_buffer(vb);
struct virtual_frame_buf *buf =
        container_of(vbuf, struct virtual_frame_buf, vb);
```

## 8. 第六步：初始化 vb2_queue

`vb2_queue` 是 streaming buffer 的核心对象。老师最终版：

```c
g_vb_queue.type = V4L2_BUF_TYPE_VIDEO_CAPTURE;
g_vb_queue.io_modes = VB2_MMAP | VB2_USERPTR | VB2_READ;
g_vb_queue.drv_priv = NULL;
g_vb_queue.buf_struct_size = sizeof(struct virtual_frame_buf);
g_vb_queue.ops = &virtul_vb2_ops;
g_vb_queue.mem_ops = &vb2_vmalloc_memops;
g_vb_queue.timestamp_flags = V4L2_BUF_FLAG_TIMESTAMP_MONOTONIC;

ret = vb2_queue_init(&g_vb_queue);
```

逐项看：

```text
type
  必须和 querycap、s_fmt 使用的视频采集类型一致。
  这里是 V4L2_BUF_TYPE_VIDEO_CAPTURE。

io_modes
  支持哪些 buffer 使用方式。老师这里支持 MMAP、USERPTR、READ。

buf_struct_size
  vb2 分配 buffer 时，不只分配通用 vb2 buffer，
  还会按这个大小分配驱动自己的 virtual_frame_buf。

ops
  vb2 在 REQBUFS/QBUF/STREAMON/STREAMOFF 等阶段要回调驱动哪些函数。

mem_ops
  buffer 内存由谁分配和映射。
  老师使用 vb2_vmalloc_memops，表示用 vmalloc 内存模拟。

timestamp_flags
  时间戳类型。
```

这里最容易错的是 `type`。普通摄像头必须用：

```c
V4L2_BUF_TYPE_VIDEO_CAPTURE
```

初始化完队列后，还要把它挂到 `video_device`：

```c
mutex_init(&g_vb_queue_lock);

g_vdev.queue = &g_vb_queue;
g_vdev.queue->lock = &g_vb_queue_lock;
```

这样 `vb2_ioctl_reqbufs/qbuf/dqbuf` 才知道操作哪一个队列。

## 9. 第七步：实现 vb2_ops

老师的 vb2 ops：

```c
static const struct vb2_ops virtul_vb2_ops = {
    .queue_setup     = virtual_queue_setup,
    .buf_queue       = virtual_buf_queue,
    .start_streaming = virtual_start_streaming,
    .stop_streaming  = virtual_stop_streaming,
    .wait_prepare    = vb2_ops_wait_prepare,
    .wait_finish     = vb2_ops_wait_finish,
};
```

这些函数分别对应 APP 的几个动作。

### 9.1 APP `REQBUFS`：触发 `queue_setup`

APP 申请 buffer：

```c
ioctl(fd, VIDIOC_REQBUFS, &req);
```

内核调用：

```text
vb2_ioctl_reqbufs
  -> vb2_core_reqbufs
  -> virtual_queue_setup()
```

老师代码：

```c
static int virtual_queue_setup(struct vb2_queue *vq,
        unsigned int *nbuffers,
        unsigned int *nplanes,
        unsigned int sizes[],
        struct device *alloc_devs[])
{
    if (vq->num_buffers + *nbuffers < 8)
        *nbuffers = 8 - vq->num_buffers;

    *nplanes = 1;
    sizes[0] = PAGE_ALIGN(800 * 600 * 2);

    return 0;
}
```

关键点：

```text
至少 8 个 buffer
  老师这里是假设至少需要 8 个。真实驱动可以按硬件流水线需要决定。

1 个 plane
  MJPEG 一帧数据放在一个连续 buffer 里，所以 nplanes = 1。

sizes[0]
  给每个 buffer 分配多大空间。
  老师用 PAGE_ALIGN(800 * 600 * 2)，这个大小足够容纳 red/green/blue
  那几张 JPEG 数组。
```

MJPEG 是压缩格式，真实每帧大小不是 `800*600*2`。这里这么写只是为了让 vmalloc buffer 足够大。

### 9.2 APP `QBUF`：触发 `buf_queue`

APP 把空 buffer 交给驱动：

```c
ioctl(fd, VIDIOC_QBUF, &buf);
```

内核调用：

```text
vb2_ioctl_qbuf
  -> vb2_core_qbuf
  -> virtual_buf_queue()
```

老师代码：

```c
static void virtual_buf_queue(struct vb2_buffer *vb)
{
    struct vb2_v4l2_buffer *vbuf = to_vb2_v4l2_buffer(vb);
    struct virtual_frame_buf *buf =
            container_of(vbuf, struct virtual_frame_buf, vb);

    list_add_tail(&buf->list, &g_queued_bufs);
}
```

这一步特别关键：`QBUF` 不是“APP 已经拿到数据”，而是“APP 交出一个空 buffer，驱动可以往里面写数据了”。

所以 `g_queued_bufs` 可以理解为：

```text
驱动当前持有的空 buffer 队列
```

真实硬件驱动中，这一步通常会把 buffer 地址交给 DMA；老师的虚拟驱动没有 DMA，所以只是挂链表。

### 9.3 APP `STREAMON`：触发 `start_streaming`

APP 启动采集：

```c
ioctl(fd, VIDIOC_STREAMON, &type);
```

内核调用：

```text
vb2_ioctl_streamon
  -> vb2_core_streamon
  -> virtual_start_streaming()
```

老师用 timer 模拟硬件开始工作：

```c
static int virtual_start_streaming(struct vb2_queue *vq,
                                   unsigned int count)
{
#if LINUX_VERSION_CODE < KERNEL_VERSION(4, 15, 0)
    setup_timer(&g_virtual_timer, virtual_timer_expire, 0);
#else
    timer_setup(&g_virtual_timer, virtual_timer_expire, 0);
#endif

    g_virtual_timer.expires = jiffies + HZ / 30;
    add_timer(&g_virtual_timer);

    return 0;
}
```

对应真实硬件时，这里通常做：

```text
打开时钟
配置寄存器
配置 DMA
使能中断
启动 sensor 或采集控制器
```

老师这里做的是：创建/设置 timer，让它 1/30 秒后触发一次 `virtual_timer_expire()`。

### 9.4 timer 到期：模拟硬件产生一帧

timer 到期函数是整个虚拟驱动“产帧”的核心。

主线逻辑：

```text
timer 到期
  -> 从 g_queued_bufs 取出一个空 buffer
  -> 获取这个 buffer 的内核虚拟地址
  -> 拷贝 red/green/blue JPEG 数据进去
  -> 设置本帧实际 payload 大小
  -> 调用 vb2_buffer_done(..., VB2_BUF_STATE_DONE)
  -> 重新设置 timer，准备下一帧
```

先取 buffer：

```c
static struct virtual_frame_buf *virtual_get_next_buf(void)
{
    struct virtual_frame_buf *buf = NULL;

    if (list_empty(&g_queued_bufs))
        goto leave;

    buf = list_entry(g_queued_bufs.next,
                     struct virtual_frame_buf, list);
    list_del(&buf->list);

leave:
    return buf;
}
```

再填数据：

```c
ptr = vb2_plane_vaddr(&buf->vb.vb2_buf, 0);

if (g_copy_cnt <= 60) {
    memcpy(ptr, red, sizeof(red));
    vb2_set_plane_payload(&buf->vb.vb2_buf, 0, sizeof(red));
} else if (g_copy_cnt <= 120) {
    memcpy(ptr, green, sizeof(green));
    vb2_set_plane_payload(&buf->vb.vb2_buf, 0, sizeof(green));
} else {
    memcpy(ptr, blue, sizeof(blue));
    vb2_set_plane_payload(&buf->vb.vb2_buf, 0, sizeof(blue));
}

vb2_buffer_done(&buf->vb.vb2_buf, VB2_BUF_STATE_DONE);
```

这里有三个关键函数：

```text
vb2_plane_vaddr()
  得到第 0 个 plane 的内核虚拟地址。
  因为老师使用 vb2_vmalloc_memops，所以可以这样拿地址并 memcpy。

vb2_set_plane_payload()
  告诉 vb2：这个 buffer 里真正有效的数据有多少字节。
  对 MJPEG 这类压缩格式，每帧大小不固定，所以 payload 应该按
  实际 JPEG 数组大小设置。

vb2_buffer_done()
  告诉 vb2：这一帧已经处理完成，APP 可以 DQBUF 取走。
```

没有 `vb2_buffer_done()`，APP 的 `VIDIOC_DQBUF` 会一直等不到完成帧。

最后重新启动 timer：

```c
mod_timer(&g_virtual_timer, jiffies + HZ / 30);
```

这样虚拟摄像头就能持续产生帧。

### 9.5 APP `DQBUF`：取回完成帧

APP 调用：

```c
ioctl(fd, VIDIOC_DQBUF, &buf);
```

这个操作主要由 vb2 完成。驱动不需要自己写 `dqbuf` 回调，因为 ioctl 表里挂的是：

```c
.vidioc_dqbuf = vb2_ioctl_dqbuf,
```

vb2 能返回数据的前提是：驱动之前已经调用了：

```c
vb2_buffer_done(&buf->vb.vb2_buf, VB2_BUF_STATE_DONE);
```

所以 APP 视角和驱动视角是这样的：

```text
APP: QBUF
  空 buffer 交给驱动

驱动: buf_queue
  挂到 g_queued_bufs

APP: STREAMON
  启动采集

驱动: timer 模拟硬件
  取一个 queued buffer
  填 JPEG 数据
  vb2_buffer_done(DONE)

APP: DQBUF
  从 vb2 取回完成 buffer
  根据 bytesused 处理图像数据

APP: 再次 QBUF
  把这个 buffer 重新交给驱动循环使用
```

## 10. 第八步：STREAMOFF 必须清理未完成 buffer

APP 停止采集：

```c
ioctl(fd, VIDIOC_STREAMOFF, &type);
```

内核调用：

```text
vb2_ioctl_streamoff
  -> vb2_core_streamoff
  -> virtual_stop_streaming()
```

老师最终版：

```c
static void virtual_stop_streaming(struct vb2_queue *vq)
{
    del_timer(&g_virtual_timer);

    while (!list_empty(&g_queued_bufs)) {
        struct virtual_frame_buf *buf;

        buf = list_entry(g_queued_bufs.next,
                         struct virtual_frame_buf, list);
        list_del(&buf->list);
        vb2_buffer_done(&buf->vb.vb2_buf, VB2_BUF_STATE_ERROR);
    }
}
```

这里有两个关键点：

```text
del_timer()
  停止模拟硬件产帧。

vb2_buffer_done(..., VB2_BUF_STATE_ERROR)
  把还在驱动队列里、没有完成的 buffer 归还给 vb2。
```

为什么 STREAMOFF 时没填完的 buffer 也要 `vb2_buffer_done()`？

因为这些 buffer 已经通过 `QBUF` 交给驱动了。只要驱动拿着不还，vb2 就认为它们还在驱动手里。停止采集时必须全部归还，否则应用退出、重新申请 buffer 或关闭设备时容易卡住或状态异常。

完成帧用：

```c
VB2_BUF_STATE_DONE
```

停止时未完成帧用：

```c
VB2_BUF_STATE_ERROR
```

这表示“这帧没有有效数据，但 buffer 已经还给框架了”。

## 11. 完整调用链

把 APP、V4L2 Core、vb2、驱动放在一起看：

```text
APP open("/dev/videoX")
  -> v4l2_fh_open

APP VIDIOC_QUERYCAP
  -> video_ioctl2
  -> virtual_querycap

APP VIDIOC_ENUM_FMT
  -> video_ioctl2
  -> virtual_enum_fmt_cap

APP VIDIOC_G_FMT / VIDIOC_S_FMT
  -> video_ioctl2
  -> virtual_g_fmt / virtual_s_fmt_cap

APP VIDIOC_REQBUFS
  -> vb2_ioctl_reqbufs
  -> virtual_queue_setup
  -> vb2 根据 vb2_vmalloc_memops 分配 buffer

APP VIDIOC_QUERYBUF
  -> vb2_ioctl_querybuf
  -> APP 得到 mmap 偏移等信息

APP mmap
  -> vb2_fop_mmap
  -> APP 映射 buffer

APP VIDIOC_QBUF
  -> vb2_ioctl_qbuf
  -> virtual_buf_queue
  -> buffer 加入 g_queued_bufs

APP VIDIOC_STREAMON
  -> vb2_ioctl_streamon
  -> virtual_start_streaming
  -> 启动 timer

timer 到期
  -> virtual_timer_expire
  -> virtual_get_next_buf
  -> vb2_plane_vaddr
  -> memcpy JPEG 数据
  -> vb2_set_plane_payload
  -> vb2_buffer_done(DONE)

APP VIDIOC_DQBUF
  -> vb2_ioctl_dqbuf
  -> 取回完成帧

APP 再次 VIDIOC_QBUF
  -> buffer 回到驱动队列，等待下一帧

APP VIDIOC_STREAMOFF
  -> vb2_ioctl_streamoff
  -> virtual_stop_streaming
  -> 停 timer，归还未完成 buffer

APP close
  -> vb2_fop_release
```

## 12. 这份虚拟驱动的关键点

### 12.1 `video_ioctl2` 是 ioctl 分发入口

驱动不是自己写一个大 `switch(cmd)`。它把：

```c
.unlocked_ioctl = video_ioctl2,
```

交给 V4L2 Core，然后通过：

```c
.ioctl_ops = &virtual_ioctl_ops,
```

告诉 V4L2 Core 每个标准命令对应哪个函数。

### 12.2 `vb2_ioctl_*` 负责通用 buffer 操作

这些 ioctl 不需要驱动重写：

```c
vb2_ioctl_reqbufs
vb2_ioctl_querybuf
vb2_ioctl_qbuf
vb2_ioctl_dqbuf
vb2_ioctl_streamon
vb2_ioctl_streamoff
```

驱动只需要实现 vb2 在关键阶段反过来调用的 ops：

```c
queue_setup
buf_queue
start_streaming
stop_streaming
```

### 12.3 `buf_queue` 的本质是“APP 把空 buffer 交给驱动”

`virtual_buf_queue()` 不填数据，只是把 buffer 放进 `g_queued_bufs`。

填数据发生在“硬件产帧”时。老师用 timer 模拟这个时刻；真实驱动可能在中断、DMA 完成回调、USB URB 完成回调里做。

### 12.4 `vb2_buffer_done()` 是驱动还帧给 APP 的分界线

只要没有调用：

```c
vb2_buffer_done(..., VB2_BUF_STATE_DONE);
```

APP 就不能通过 `DQBUF` 得到这一帧。

这句话可以理解成：

```text
驱动 -> vb2：这块 buffer 已经处理完了。
vb2 -> APP：DQBUF 可以返回了。
```

### 12.5 `bytesused` 来自 payload

APP `DQBUF` 后看到的有效数据大小，来自驱动设置的 payload：

```c
vb2_set_plane_payload(&buf->vb.vb2_buf, 0, sizeof(red));
```

对 MJPEG 来说，这个值应该等于实际 JPEG 文件大小，而不是固定的 `width * height * 2`。

### 12.6 `STREAMOFF` 时要归还所有驱动持有的 buffer

停止采集时，`g_queued_bufs` 里可能还有 APP 交给驱动、但 timer 没来得及填的 buffer。必须全部：

```c
vb2_buffer_done(..., VB2_BUF_STATE_ERROR);
```

否则 buffer 生命周期不闭合。

## 13. 从虚拟驱动迁移到真实硬件驱动

老师这份代码里的“虚拟硬件”是：

```text
timer + red/green/blue 数组 + memcpy
```

真实硬件驱动要替换的是这些地方：

```text
virtual_start_streaming()
  虚拟驱动：启动 timer
  真实驱动：配置硬件、启动 DMA/USB/MIPI 接收、打开中断

virtual_buf_queue()
  虚拟驱动：把 buffer 挂到 g_queued_bufs
  真实驱动：把 buffer DMA 地址交给硬件，或加入硬件待处理队列

virtual_timer_expire()
  虚拟驱动：timer 到期后 memcpy JPEG 数组
  真实驱动：中断 / DMA done / URB complete 表示一帧完成

vb2_plane_vaddr()
  虚拟驱动：vmalloc 内存可以直接拿虚拟地址 memcpy
  真实 DMA 驱动：通常使用 dma-contig 或 scatter-gather，需要 DMA 地址

vb2_buffer_done()
  虚拟驱动和真实驱动都必须调用。
  区别只是调用时机：虚拟驱动在 timer 中；真实驱动在硬件完成一帧时。
```

保留下来的主线不变：

```text
APP QBUF
  -> buffer 进入驱动

硬件完成一帧
  -> 驱动设置 payload / sequence / timestamp
  -> vb2_buffer_done()

APP DQBUF
  -> APP 取走完成帧
```

## 14. 学这份代码时最容易混的点

### 14.1 `V4L2_BUF_TYPE_VIDEO_CAPTURE` 要贯穿一致

普通摄像头采集要使用：

```c
V4L2_BUF_TYPE_VIDEO_CAPTURE
```

它应该出现在：

```text
querycap 的能力声明
s_fmt/g_fmt 的 type 检查
vb2_queue.type
APP 的 reqbuf/qbuf/dqbuf/streamon 参数
```

只要其中一处类型不一致，APP 和驱动就可能对不上。

### 14.2 `S_FMT` 和 `G_FMT` 都有用

`S_FMT` 表示 APP 请求设置格式，驱动可以接受、拒绝或修正参数。

`G_FMT` 表示 APP 查询当前格式。很多程序依赖它，所以最终版补了：

```c
.vidioc_g_fmt_vid_cap = virtual_g_fmt,
```

### 14.3 `queue_setup` 只说明 buffer 分配要求

它不启动硬件，也不填数据。它只回答：

```text
需要几个 buffer
每个 buffer 几个 plane
每个 plane 多大
```

### 14.4 `buf_queue` 不是完成帧

`buf_queue` 只是表示“这个 buffer 可以给驱动用了”。完成帧必须等驱动调用 `vb2_buffer_done()`。

### 14.5 timer 只是模拟中断

这份虚拟驱动里没有真实硬件，所以用 timer 定期调用 `virtual_timer_expire()`。

真实摄像头驱动里，同等位置通常是：

```text
硬件中断处理函数
DMA 完成回调
USB URB complete 回调
CSI/MIPI frame done 回调
```

### 14.6 MJPEG 的 `bytesused` 是实际压缩帧大小

虽然分辨率是 `800x600`，buffer 分配大小是 `PAGE_ALIGN(800*600*2)`，但一帧 MJPEG 的有效数据大小是：

```c
sizeof(red)
sizeof(green)
sizeof(blue)
```

所以要用 `vb2_set_plane_payload()` 设置实际大小。

## 15. 一句话总结

老师这份虚拟摄像头驱动的核心不是图像算法，也不是复杂硬件，而是让你看懂 V4L2 capture 驱动的生命周期：

```text
注册 video_device 生成 /dev/videoX
  -> 用 ioctl_ops 回答设备能力和格式
  -> 用 vb2_queue 管理 APP 申请的 buffer
  -> APP QBUF 后驱动拿到空 buffer
  -> STREAMON 后模拟硬件开始产帧
  -> 一帧完成时填 buffer 并 vb2_buffer_done()
  -> APP DQBUF 取走完成帧
  -> STREAMOFF 停止硬件并归还剩余 buffer
```

只要这条线理顺了，后面看真实 USB 摄像头、MIPI CSI 驱动时，就能把复杂硬件部分放到对应位置上：哪里是启动硬件，哪里是把 buffer 交给硬件，哪里是一帧完成，哪里调用 `vb2_buffer_done()`。
